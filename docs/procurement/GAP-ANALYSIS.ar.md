# ملف المشتريات — مقارنة المقترحات بما هو موجود، وقرار التنفيذ

المصدر: «النموذج المقترح لسلسلة وسيناريو المشتريات في نظام ERP OPS» (تقرير مرفق، 2026-10-11).
المنهج: كل مقترح قورن بالكود الفعلي (`app/Services/Procurement`, `app/Services/Inbound`, `app/Services/Master`) لا بالذاكرة.
**ما هو موجود لا يُمسّ. ما يُضاف يُبنى بنفس أنماط النظام (خدمة + صلاحية + سجل تدقيق + اختبار).**

## 1) السلسلة المعتمدة (13 مرحلة) — الحالة

| # | المرحلة في التقرير | الحالة في النظام | القرار |
|---|---|---|---|
| 1 | طلب احتياج شراء PR | موجود: مسودة ← إرسال ← مراجعة ← اعتماد/رفض بسبب، بنود متعددة، تاريخ حاجة، أولوية، مركز تكلفة، مبرر، سجل تدقيق | يبقى |
| 2 | مراجعة الإدارة المختصة حسب سلّم | سلسلة اعتماد PR ثابتة (المشتريات فقط) | **يُضاف:** سلّم اعتماد PR حسب القيمة التقديرية من الإعدادات (`procurement.prApprovalTiers`) بنفس آلية أوامر الشراء |
| 3 | اعتماد طلب الشراء | موجود (دور كل خطوة يُتحقق منه) | يبقى + **يُضاف:** منع اعتماد الشخص لطلبه هو (فصل المسؤوليات) |
| 4 | طلب عروض سعر RFQ | موجود: من PR أو مباشرة، دعوة موردين، تسجيل العروض بمرفق، تاريخ إغلاق، صلاحية العرض | يبقى. إرسال RFQ بالبريد: مؤجل (منصة البريد «Integration Pending» على مستوى النظام كله) |
| 5 | مقارنة العروض | موجود: مقارنة مرجّحة (السعر 50% / المهلة 30% / تقييم المورد 20%) مع أسباب مكتوبة لكل عرض | يبقى + **يُضاف:** تكلفة الشحن والضمان في العرض وفي المقارنة (الإجمالي الفعلي لا سعر الوحدة فقط) |
| 6 | اعتماد المورد والعرض | موجود: ترسية بعرض واحد مع استثناء موثّق لتقييم مورد منخفض | **يُضاف:** الحد الأدنى لعدد العروض (`procurement.minQuotes`) مع مبرّر استثناء إلزامي، وسبب إلزامي عند اختيار عرض غير العرض الموصى به |
| 7 | إصدار أمر شراء PO | موجود: من PR أو من ترسية RFQ أو يدويًا، مرجع PR/RFQ، شروط دفع، مستودع، تاريخ توريد | يبقى + **يُضاف:** خصم وشحن وضريبة على مستوى الأمر وإجمالي شامل |
| 8 | اعتماد أمر الشراء | **موجود** (التقرير ذكر أنه غير موجود): سلّم اعتماد حسب القيمة من الإعدادات، خطوات بأدوار، رفض بسبب | يبقى + منع اعتماد منشئ الأمر لأمره |
| 9 | استلام المشتريات | موجود: شحنة متوقعة من الأمر ← وصول ← فحص ← GRN، مسح باركود الأمر، استلام جزئي بسندات متعددة على الأمر نفسه | يبقى |
| 10 | فحص الكميات والجودة | موجود: مقبول/تالف/مرفوض لكل بند، دفعة وصلاحية إلزاميتان للأصناف المتتبَّعة، الزيادة مرفوضة إلا بإعداد `receiving.allowExcess`، استثناءات للنقص والمرفوض | يبقى |
| 11 | إضافة للمخزون والمستودع | موجود: الحركة المخزنية في معاملة واحدة مع GRN، منطقة استلام ← مهام putaway بموقع مقترح حسب فئة التخزين، التالف محجور، المرفوض لا يدخل المخزون | يبقى |
| 12 | مطابقة الفاتورة (ثلاثية) | **غير موجود** | **يُضاف:** تسجيل فاتورة المورد ومطابقتها مع الأمر وسندات الاستلام (كمية وسعر) مع حدود سماح، وحالات مطابقة/مختلف عليها/معتمدة للصرف |
| 13 | المستحقات وسداد المورد | غير موجود | **يُضاف جزئيًا:** قائمة مستحقات بتاريخ الاستحقاق من شروط الدفع + تسجيل السداد (تاريخ ومرجع). تنفيذ الدفع البنكي نفسه خارج هذا النظام (نظام مالي/خزينة) |

| المقترح | الحالة | القرار |
|---|---|---|

| تسجيل هوية المعتمد والتاريخ والملاحظات ونسخة من البيانات المعتمدة | موجود (جدول خطوات + سجل تدقيق؛ البنود لا تُعدَّل بعد الإنشاء) | يبقى |

| عودة الطلب لصاحبه للتعديل | الرفض نهائي بسبب؛ لا «طلب تعديل» | مؤجل (يكفي حاليًا الرفض ثم طلب جديد) |

| **فصل المسؤوليات** | لا يمنع النظام اعتماد الشخص لطلبه/أمره | **يُضاف** (`procurement.allowSelfApproval` = false) |

## 6) الاستلام والفحص والترحيل

كل بنود التقرير هنا موجودة ومختبَرة: ربط الاستلام بأمر شراء إلزاميًا، سند لكل دفعة، الزيادة لا تُقبل تلقائيًا، الفصل بين «وصل» و«قُبل»، التالف والمرفوض لا يدخلان المتاح، الترحيل معاملة واحدة تحدّث الأرصدة والحركات وكميات الأمر وحالته. **لا تغيير.**
غير موجود ومؤجل: فصل المستلم عن الفاحص كأشخاص (يُضبط بالصلاحيات حاليًا)، «يحتاج إعادة فحص»، شهادة استلام PDF للمورد.

## 7) أنواع الأرصدة

فعلي / محجوز / مخصص / متاح / حجر / تالف / منتهي / منطقة الاستلام / بالطريق (تحويلات) / مرتجع — **كلها موجودة في محرك المخزون** ويقرؤها نظام المبيعات عبر التكامل. لا تغيير.

## 8) الفواتير والمستحقات — ما سيُبنى

- **تسجيل فاتورة مورد** على أمر شراء: رقم الفاتورة وتاريخها، تاريخ الاستحقاق (من شروط الدفع أو يدويًا)، بنود بكمية وسعر وضريبة، إجمالي.
- **مطابقة ثلاثية آلية:** كمية الفاتورة ≤ المستلم المقبول غير المفوتَر، سعر البند = سعر الأمر ضمن سماح (`procurement.invoiceTolerancePct`)، الإجمالي ضمن السماح. أي فرق ← حالة «مختلف عليها» مع تفاصيل الفرق؛ لا تُعتمد للصرف إلا بقرار موثّق.
- **الاعتماد للصرف** (صلاحية `invoice.approve`) ← **تسجيل السداد** (`invoice.pay`: تاريخ ومرجع) ← مسدَّدة. **التنفيذ البنكي خارج النظام.**
- لوحة: فواتير غير مطابقة، فواتير مستحقة خلال 7 أيام، قيمة المستحقات المفتوحة.

## 9) الصلاحيات

| الدور في التقرير | في النظام |
|---|---|
| مقدم الطلب | `pr.create` (مدير المستودع، المشتريات) |
| مدير الإدارة | لا كيان إدارات — سلّم اعتماد PR الجديد يغطي الدور بالأدوار الموجودة |
| مسؤول المشتريات | `proc` |
| صاحب الصلاحية المالية | `finance` / `gm` في سلّم الاعتماد |
| أمين المستودع | `shipment.receive`, `grn.post`, `putaway.confirm` |
| مسؤول الجودة | نتيجة الفحص ضمن `grn.post` (مؤجل فصله) |
| المحاسب / الحسابات الدائنة / الخزينة | **جديد:** `invoice.register` (المشتريات، المالية)، `invoice.approve` (المالية، المدير العام)، `invoice.pay` (المالية) |
| مدير النظام | `super` — لا يتجاوز فصل المسؤوليات |

## 10) لوحة المؤشرات

موجود: PR بانتظار، RFQ مفتوحة، PO بانتظار (حسب الخطوة)، شحنات متوقعة، مُرسلة بانتظار تأكيد، اقتراحات عاجلة.
**يُضاف:** قيمة أوامر الشراء المفتوحة، الأوامر المتأخرة، قيمة المستلم هذا الشهر، متوسط دورة الشراء (من إرسال الطلب إلى إرسال الأمر)، فواتير غير مطابقة ومستحقة.
مؤجل: وفورات الشراء (تحتاج سعرًا مرجعيًا معتمدًا لكل صنف)، نسبة المرتجعات للمورد (تحتاج مستند مرتجع للمورد).

## 11) مؤجل بقرار صريح (وسببه)

| البند | السبب |
|---|---|
| البريد الإلكتروني (RFQ، أمر الشراء، شهادة الاستلام) وملفات PDF والمرفقات | تعتمد على مزوّد بريد وتخزين ملفات غير مربوطين بعد؛ النظام يسجّل الحدث ويعرض «Integration Pending» بدل ادعاء الإرسال |
| كيان الإدارات ومديريها ومراكز التكلفة كجدول | قرار تنظيمي لم يُحسم («يُحدَّد لاحقًا») |
| تقسيم الترسية على أكثر من مورد | التقرير يشترط «إن سمحت السياسة»؛ يُضاف عند الحاجة |
| العملات، التقييم المحاسبي، القيود المحاسبية، تنفيذ الدفع البنكي | اختصاص النظام المالي |
| مرتجعات الموردين كمستند مستقل | المرفوض يُرفع حاليًا كاستثناء بقرار؛ يُبنى مع إشعار الخصم لاحقًا |

## 12) ترتيب التنفيذ

1. ضوابط الاعتماد: فصل المسؤوليات، سلّم PR، الحد الأدنى للعروض وسبب الاختيار، الشحن والضمان في العروض.
2. أمر الشراء: الخصم/الشحن/الضريبة، المتابعة والتأخير والتنبيه، مؤشرات اللوحة.
3. البيانات الرئيسية: وحدة الشراء ومعامل التحويل، ملف المورد (بنك، حد ائتماني، عنوان، حالة، مستندات) والبوابة.
4. فواتير الموردين والمطابقة الثلاثية والمستحقات.
5. الواجهات، الاختبارات على MySQL وPostgreSQL، التوثيق، النشر.
