# دليل الفريق — B2B ops (Laravel + Vue)

هذا الدليل يكفي لتشغيل النظام على جهازك والبدء بالعمل عليه. التفاصيل الأعمق في:
[CONVENTIONS.md](CONVENTIONS.md) (الخادم) · [FRONTEND.md](FRONTEND.md) (الواجهة) · [RUNBOOK.md](RUNBOOK.md) (التشغيل والنشر).

## 1. التشغيل لأول مرة — أمر واحد

المتطلبات: **PHP 8.3** و **Composer 2**، ومعهما إما **Docker Desktop** أو خادم **MySQL 8** عندك. (Node 20+ مطلوب فقط عند تعديل الواجهة.)

</div>

```bash
git clone https://github.com/salem-cell/scm-ops-laravel.git
cd scm-ops-laravel
php tools/setup.php --docker
php artisan serve --port=8000
```

<div dir="rtl">

ثم افتح <http://127.0.0.1:8000>. السكربت يقوم بكل شيء: تنزيل المكتبات، إنشاء `.env`، **توليد كل الأسرار على جهازك**
(`APP_KEY` و`JWT_ACCESS_SECRET` وكلمة مرور قاعدة البيانات وكلمة مرور الحسابات التجريبية)، تشغيل MySQL، إنشاء الجداول،
تحميل البيانات التجريبية، ثم يطبع لك كلمة المرور في آخره.

- **بدون Docker؟** أنشئ قاعدة البيانات بنفسك (أوامر SQL يطبعها السكربت إن فشل الاتصال)، ضع بياناتها في `.env` ثم
  شغّل `php tools/setup.php`.
- **إعادة التشغيل آمنة:** السكربت لا يغيّر قيمة موجودة في `.env` ولا يمسح بيانات. المسح وإعادة التحميل فقط مع `--fresh`.
- **لماذا لا يوجد `.env` في المستودع؟** لأنه يحمل الأسرار. كل مطوّر له ملفه، وبيئة الإنتاج لها ملفها. هذا مقصود ولا يتغير.

### الحسابات التجريبية

`admin` (كل الصلاحيات) · `sales` · `wm` مدير مستودع · `inv` مراقب مخزون · `proc` مشتريات · `disp` موزّع · `worker` عامل ·
`driver` سائق · `gm` مدير عام · `finance` مالية — كلمة المرور لها جميعًا هي `SEED_PASSWORD` في ملف `.env` عندك.

## 2. العمل اليومي

| ماذا | الأمر |
|---|---|
| تشغيل الخادم | `php artisan serve --port=8000` |
| تعديل الواجهة مع تحديث فوري | `npm run dev` (في نافذة ثانية) |
| كل اختبارات الخادم | `php artisan test` |
| اختبارات مجال واحد | `php artisan test tests/Feature/Sales` |
| فحص ملفات الواجهة | `node tools/check-vue.mjs resources/js` |
| بناء الواجهة للإنتاج | `npm run build` |
| مطابقة سجل المخزون مع الأرصدة | `php artisan scm:reconcile` |
| إعادة البيانات التجريبية كما كانت | `php tools/setup.php --fresh` |
| تشغيل/إيقاف قاعدة Docker | `docker compose up -d` / `docker compose down` |

**مهم عند تعديل الواجهة:** مجلد `public/build` مرفوع في المستودع حتى يعمل النظام مباشرة بعد الاستنساخ. بعد أي تعديل في
`resources/js` أو `resources/css` شغّل `npm run build` وارفع الناتج مع نفس الـ commit.

## 3. خريطة المشروع

| المسار | المحتوى |
|---|---|
| `routes/api/*.php` | مسارات الـ API (250 مسارًا) مقسّمة حسب المجال، وكل مسار عليه صلاحيته `perm:…` |
| `app/Http/Controllers/Api` | متحكمات رفيعة: تحقق من المدخلات ثم استدعاء الخدمة |
| `app/Services/<المجال>` | منطق العمل كله هنا (مبيعات، مشتريات، استلام، تجهيز، نقل، مرتجعات…) |
| `app/Services/Inventory/InventoryService.php` | **المكان الوحيد** الذي يغيّر أرصدة المخزون — داخل معاملة، مع قفل، ويكتب سجل الحركات |
| `app/Support` | الأخطاء الموحدة `AppError`، المستخدم الحالي `AuthUser`، آلات الحالة `Sm`، الترقيم |
| `config/scm.php` و `resources/js/shared/constants.json` | الثوابت المشتركة (الحالات، الانتقالات، التسميات) — مولّدة، لا تُعدّل يدويًا |
| `resources/js/pages/<المجال>` | صفحات Vue (33 صفحة) · `resources/js/components` المكوّنات المشتركة · `/kit` صفحة مثال حي |
| `tests/Feature` | اختبارات على MySQL حقيقي، منها `AcceptanceTest` (القصة الكاملة من الشراء حتى التسليم) |
| `docs/reference` | مخطط النظام المرجعي الذي نُقل عنه هذا النظام |

## 4. قواعد لا تُكسر

1. **المخزون:** لا تعدّل جداول الأرصدة مباشرة أبدًا — دائمًا عبر `InventoryService`. لا بيع زائد، لا استلام زائد، والسجل يطابق الأرصدة دائمًا.
2. **الصلاحيات على الخادم:** إخفاء زر في الواجهة ليس حماية. كل مسار جديد يأخذ `perm:<key>` واختبارًا سلبيًا (مستخدم بلا صلاحية ← 403).
3. **الصدق في التكاملات:** ما لم يُربط فعليًا يظهر `integration_pending`. لا «تم الإرسال» ولا «مباشر» وهميًا.
4. **لا أسرار في الكود** ولا في `.env.example`. لا `env()` خارج مجلد `config/`.
5. **الأخطاء بشكل واحد:** `{category, code, message, messageEn, details, requestId}` عبر `AppError` — رسالة عربية وإنجليزية.
6. **العمليات الحساسة idempotent:** الواجهة ترسلها بـ `api.postIdempotent` والمسار عليه `idempotent`.
7. **الواجهة:** لا `window.prompt/alert/confirm` (استخدم `confirm()` و`ask()` من `stores/ui.js`)، ولا مكوّنات lazy داخل الـ render. الفاحص يرفضها.
8. **لا نقول «100%» أو «جاهز للإنتاج» بلا دليل:** اختبار ناجح، أو لقطة، أو سجل.

## 5. طريقة العمل على GitHub

- فرع لكل مهمة: `feature/…` أو `fix/…` ثم Pull Request إلى `main`.
- كل PR يشغّل الفحص الآلي (CI): اختبارات الخادم على MySQL، وفحص الواجهة وبناؤها، وتجربة إعداد مطوّر جديد من الصفر. لا دمج قبل أن يخضرّ.
- أي إصلاح لخلل يأتي معه اختبار يثبت الخلل ثم يثبت الإصلاح.

## 6. ما لم يكتمل بعد (مفتوح كـ Issues في المستودع)

- **الخرائط مربوطة (Mapbox)**: ضع الرمز العام `MAPBOX_PUBLIC_TOKEN=pk.…` في ملف `.env` عندك (اطلبه من مدير المشروع — لا يُكتب في المستودع)، وبدونه تظهر الخرائط بحالة Integration Pending. التفاصيل في `docs/FRONTEND.md` قسم Maps.
- ربط التكاملات الخارجية المتبقية: تتبع GPS الحي للمركبات، تخزين الملفات (صور وتواقيع POD)، واتساب/الإشعارات، الـ ERP — كلها الآن `integration_pending` والإعدادات جاهزة في `config/integrations.php`.
- الاستضافة وبيئة الإنتاج (تحتاج PHP 8.3 و MySQL 8 — خطوات النشر في RUNBOOK).
- إنشاء حساب المدير الأول للإنتاج وإيقاف الحسابات التجريبية.
- اختبارات متصفح آلية دائمة (Playwright) بدل الفحص اليدوي/المؤقت.
